# 部署与持续监督：量化系统上线流程


> **英文摘要（English summary）：** A release and operating workflow for quantitative strategies, from versioned research artifacts and pre-trade gates to production monitoring, incident response, suspension, and rollback. It focuses on decisions and handoffs across the lifecycle.

> **文件定位**：本文件按量化策略从研究完成到生产运行的顺序组织，说明先固化什么、如何上线、哪些门槛控制风险、上线后持续看什么、故障时怎样处置。它与[实务手册](./实务.md)分工不同：流程篇串起执行步骤；实务篇解释系统架构、部署形态、监控指标、代码和 A 股/美股规则差异。
>
> **书籍依据**：《Advances in Financial Machine Learning》第1、2、10、11、15、16、19—22章；跨专题映射见根目录《机器学习算法与量化专题映射.md》，本专题的逐页核对见配套实务手册。书中直接讨论金融数据结构、计算效率、搜索和高性能计算；生产治理、风控、发布、告警、回滚和模型漂移部分是面向当代量化系统的实务扩展。
>
> **规则核验日期**：2026-09-28。证券市场规则、券商接口和报告要求随市场、产品、机构身份与日期变化，发布前必须核对当日有效的规则及接入协议。

## 一、生产运行要保证什么

上线目标不是“模型能定时跑”，而是持续、可核验地完成完整决策链：

~~~text
数据按时到达且可验证
  → 使用指定版本生成点时特征与预测
  → 风控独立检查组合和订单
  → 订单按市场/券商接口可靠送达、更新和撤销
  → 成交与现金/持仓账本一致
  → 状态、收益、风险、成本、系统健康可观察
  → 异常触发限单、停新单、撤单或回滚
  → 事件与版本留下可复算记录
~~~

生产策略必须同时满足四项约束：

1. **投资约束**：策略在目标市场、规模、容量、风险预算和交易成本内成立。
2. **时间约束**：输入在决策时点已可用，预测、审批、订单和成交按正确顺序发生。
3. **操作约束**：系统能处理重复、延迟、乱序、断线、部分成交、重启和供应商更正。
4. **治理约束**：谁批准、谁操作、谁监控、谁有权停机，以及如何恢复都已定义。

部署节奏要匹配策略速度。日频策略未必需要微秒级架构；低延迟策略也不能用“每天收盘检查一次”的监督频率。先由策略时钟和失败后果定义SLO，再确定技术栈。

## 二、量化上线主链

~~~text
研究结果通过主题四放行门槛
  → 写生产策略规格、责任人、权限和运行目标
  → 冻结代码、模型、特征、数据、依赖与规则版本
  → 选择批处理/流式/低延迟部署形态
  → 建立点时数据契约、特征一致性与时间同步
  → 实现独立的订单前风控与账户额度约束
  → 接入订单管理、成交回报和持仓现金账本
  → 做离线重放、故障演练、影子和纸面运行
  → 小范围canary发布，逐级放量并设自动停止条件
  → 持续监控数据、模型、策略、执行、账户和基础设施
  → 事件分级、kill switch、回滚、复盘和责任追踪
  → 按审批流程更新数据/模型/策略/规则并重新验收
~~~

## 三、按先后顺序执行

### 第1步：先写生产策略规格，不直接搬研究笔记

将研究交付转成不可歧义的策略说明。至少记录：

| 生产规格 | 需要写清 |
|---|---|
| 身份与版本 | 策略名、唯一策略ID、owner、代码/模型/特征版本 |
| 市场范围 | A股/美股、证券类别、交易所/场所、证券池、账户和币种 |
| 决策时钟 | 数据截点、信号频率、运行窗口、最迟下单时点、节假日和时区 |
| 交易定义 | 目标仓位、订单类型、价格/数量取整、退出/换仓规则、卖空约束 |
| 组合风险 | 毛/净敞口、单名/行业/市场集中度、杠杆、损失和流动性上限 |
| 成本和容量 | 费率、价差/冲击、参与率、融资/借券、目标资本规模 |
| 停止条件 | 数据过期、净值/持仓异常、风险超限、下单/回报异常的动作 |
| 责任和权限 | 运行、审批、值班、合规、风控、恢复权限及升级链路 |

研究文件里的默认值不是生产参数。需显式确认初始持仓、现金、订单在交易日边界的行为、市场关闭/重启后是否补发、模型缺特征时的降级路径以及信号失效时如何处理已有仓位。

### 第2步：检查策略研究放行条件

上线申请应附主题四的审计结论：锁定前向样本、成本后结果、容量/风险、选择偏差、交易可行性、点时数据、代码版本和未解决限制。把“研究有效”与“可运行”区分开，未通过账本、执行或风险门槛不能因回测收益高而跳过。

为每个假设标记证据等级：已用历史数据验证、依赖代理数据、模拟估计、待实盘校准。待验证的券源、滑点、延迟、借券费或数据 SLA 应设置较小风险预算和明确复核日期。

### 第3步：按策略速度选部署架构

| 策略类型 | 常用部署形态 | 重点约束 |
|---|---|---|
| 日/周/月频组合 | 定时批处理、交易日任务编排 | 财报/宏观可用时间、日历、批次重跑、开盘前风控 |
| 分钟/事件驱动 | 流式消费者或短周期调度 | 延迟、乱序、重复事件、队列积压、断线恢复 |
| 订单执行算法 | 事件驱动OMS/EMS与交易所/券商适配层 | 订单状态、撤单确认、部分成交、速率限制、价格和数量约束 |
| 低延迟策略 | 专用进程/主机、低延迟行情和交易链路 | 时钟、丢包、尾延迟、确定性、场所/券商SLA、独立熔断 |

高吞吐与低延迟是不同目标。批量分析可以把大量任务并行；实时下单链路通常要控制队列、内存分配和网络跳数。不要为了“用上HPC”增加生产依赖；先量需求、剖析瓶颈、再选择复杂度最低的架构。

### 第4步：把数据和特征做成带契约的生产输入

每类输入定义字段、单位、币种、时区、更新频率、可用时间、修订策略、缺失标记、质量阈值、来源和责任人。原始、标准化、特征和预测层分开保留，线上数据不能覆盖研究快照。

每个运行批次保存：

- 输入文件/消息的版本或内容哈希、供应商和到达/处理时间；
- 交易日、事件时间、可用时间、水位线和缺失/迟到数据清单；
- 特征生成器、模型和配置版本；
- 样本数、证券数、空值/异常数及与预期范围的比较；
- 对关键特征进行离线—在线一致性抽样。

数据延迟超出策略容忍时，默认拒绝新信号或转入预先批准的保守模式；不得把昨天的特征静默复制为今天的新值。修订/回补数据只能触发重算标记，不应覆盖原生产决策所见版本。

### 第5步：让模型发布可复现且可回滚

一次发布应是不可变的版本包，绑定：

- 源码提交/构建哈希、模型权重、特征清单和顺序；
- 训练数据截止日、训练/验证区间、随机种子和校准器；
- 依赖、运行时、CPU/GPU/精度要求、资源限制；
- 风控规则、交易日历、费率、证券池和券商/场所配置；
- 预期输入输出schema、数值边界、SLO和回滚版本。

先在生产同构环境重放历史事件，确认特征、预测和决策可与冻结研究结果逐条对齐。若硬件精度、并发归约或依赖版本造成小数差异，设定经批准的容忍范围，不能只检查最终收益看起来“差不多”。

### 第6步：独立实现订单前风险闸门

风控代码与alpha信号分离，并在订单到达券商/场所前执行。按策略、账户、证券和全组合设置：

- 订单金额/数量上限、价格保护带、单名/行业集中度；
- 毛/净敞口、杠杆、现金、保证金和可卖数量；
- 参与率/流动性限制、做空券源与借券约束；
- 重复订单/自成交风险、订单频率、撤改单速率；
- 证券状态、交易时段、停牌/价格限制、数据新鲜度；
- 当日损失、回撤、资金占用和异常订单的限额。

限额采用独立、可审计配置，拒绝原因要记录。风险数据过期、持仓对账失败、行情状态不确定或风险服务不可用时，采用预先指定的fail-closed逻辑，不让alpha服务自行绕过。订单重放使用幂等键；网络超时后先查询原订单状态，再决定是否重试，防止重复下单。

### 第7步：用状态机接订单和成交

每笔委托按可追踪状态变化处理：

~~~text
CREATED → RISK_APPROVED → SUBMITTED → ACKNOWLEDGED
  → PARTIALLY_FILLED → FILLED
  → CANCEL_REQUESTED → CANCELED / REJECTED / EXPIRED
~~~

本地订单状态与券商回报可能不同步。保存客户端订单ID、券商/交易所订单ID、原订单和改单关系、事件序号、时间戳、成交编号、拒单原因和剩余量。系统重启后先从券商同步未完成订单与成交，再接收新信号。超时撤单要等确认；不能因本地“已撤”就假设市场订单已消失。

### 第8步：将持仓、现金、公司行为和成本逐日对账

成交是权威事件之一，不是完整的账户账本。账本还要处理手续费、规费/税费、融资、借券、股息、拆股、并购、汇兑、交收和外部资金流。每一运行周期核对：

- 本地订单/成交与券商/托管回报；
- 证券数量、可卖数量、现金和应收应付；
- 毛/净敞口、保证金、币种和估值时间；
- 策略级PnL、费用和组合净值；
- 未解释的差异、重复事件或缺失回报。

差异超过预设阈值时冻结新单或降低风险预算，先查明是否为延迟、映射、公司行为还是账本bug。不能为保持图表平滑而把差异抹平。

### 第9步：按测试金字塔逐级验收

1. **单元/属性测试**：边界、单位、时区、重复ID、空数据、订单合法性。
2. **回放测试**：历史消息按真实到达顺序重放，包含迟到、重复、修订和错序。
3. **集成测试**：行情、特征、模型、风控、OMS、券商仿真和账本端到端。
4. **故障注入**：断网、API限频、进程崩溃、磁盘满、队列积压、时钟偏差、数据字段变化。
5. **压力测试**：开盘/收盘消息峰值、单一证券极端订单、撤单风暴和多策略同时下单。
6. **安全/权限测试**：凭据失效、越权、配置误改、未经批准的模型/参数发布。
7. **影子/纸面**：实时生成信号但不影响真实账户，或使用明确隔离的模拟账户。

每项测试要有预期状态、日志证据、通过人及失败后修复。测试“服务进程还活着”不代表完整交易链可用。

### 第10步：分阶段放量，每一阶段可停止和退回

~~~text
离线重放
  → 生产影子（不发单）
  → 纸面/券商模拟
  → 极小规模canary
  → 按预设风险档位逐步扩大
  → 常规运行
~~~

每阶段先检查信号/订单数量、拒单、延迟、成交率、费用、持仓差异、敞口和收益对账。进入下一阶段由策略、风控和运营共同签字；仅有策略作者批准不够。Canary通过逐笔损失上限、单名限额和账户总敞口限制损失范围。

放量触发条件必须数字化且预先锁定，例如对账差异、输入过期、订单拒绝比例、尾延迟、异常成交或回撤超过阈值。阈值按策略和历史分布确定，不存在所有系统通用的秒数/bps阈值。

### 第11步：上线后持续监控五层状态

| 监控层 | 代表指标 |
|---|---|
| 数据 | 新鲜度、缺失率、重复/乱序、延迟、schema变化、证券覆盖 |
| 模型 | 特征分布、分数/概率分布、校准、预测稳定性、漂移与模型版本 |
| 策略 | 信号数、目标仓位、换手、PnL、回撤、风险暴露、容量与规则状态 |
| 执行 | 订单确认、拒单/撤单、成交率、部分成交、滑点、冲击、延迟与券源 |
| 平台/治理 | 服务存活、队列滞后、CPU/内存/磁盘、错误率、凭证到期、权限和配置变更 |

区分指标的检测时点：数据/订单延迟可近实时监控；收益质量需等持仓期或标签成熟后判断；未成熟标签不能被当成失败，也不能被误报为成功。将无数据、静默、零交易和策略自然空仓区分。

### 第12步：预先设计分级告警、停机和恢复

- **观察级**：偏离基线但未触发硬风险，记录并由值班人员检查。
- **限制级**：数据、成本或漂移指标恶化，禁止扩仓、降低额度或只允许减仓。
- **停止新单级**：关键输入过期、持仓/成交无法对账、模型版本不匹配、风险闸门失效；拒绝新开仓，按批准规则管理未完成订单。
- **紧急级**：重复/失控下单、异常敞口、重大系统/安全事件；触发账户/策略kill switch，通知责任人和券商/运营。

停止算法不等于自动市价清仓。撤单、冻结新单、减仓或平仓由策略特征、流动性、市场状态和风险预案决定；强行平仓也可能放大冲击。停机后先同步券商订单、核对真实持仓、确认数据/模型/配置，再按最后一个已批准版本恢复。

### 第13步：监控机制稳定性，不以频繁重训掩盖退化

监控输入分布漂移、分数漂移、校准误差、收益/成本变化、执行质量和风险暴露，但漂移不是“模型应该自动重训”的同义词。确认：
1. 数据供应/定义是否变化；
2. 市场机制、证券池或流动性是否改变；
3. 标签是否已经成熟且时间对齐；
4. 净收益退化是信号、成交、成本、风险还是会计造成；
5. 再训练的候选是否重新经过数据切分、回测可信度、压力测试和审批。

先区分监控告警与策略失效；确认机制改变后再决定缩仓、暂停、复训或下架。

### 第14步：每次变更都走影响评估和重验

数据供应商、特征schema、代码依赖、模型权重、阈值、股票池、券商API、市场规则和风险限额的变化都应有变更单、差异说明、测试证据、审批、发布时间、回滚版本和影响监控。热修复也要补审计记录。

根据影响面选验收范围：仅日志展示变化可小范围回归；订单路径、模型或仓位变化需重跑完整回放/风控/影子；市场规则或账户权限变化需规则合规和接口验证。严禁生产进程自行下载“最新模型”而没有版本批准。

### 第15步：运行审计和复盘闭环

每次决策留下足以复算的时间戳、数据版本、特征、模型、预测、风险检查、订单状态、成交、费用、持仓、PnL和运行配置。所有用户/服务身份、权限、访问和参数改变留可查询日志。

故障后记录时间线、影响账户/证券、损失和未成交风险、检测时延、根因、临时处置、永久修复和测试补充。将复盘结论转成监控、边界测试、文档或限额，而不只写成事件说明。

## 四、A股与美股的上线适配

| 主题 | 共用控制 | A股配置 | 美股配置 |
|---|---|---|---|
| 规则/报告 | 保存主体、账户、市场、产品及有效时间 | 程序化交易报告、证券交易所细则、交易单元/系统接入和报告义务 | 经纪商/ATS/直接市场接入条件；Reg SHO、Reg NMS等按活动适用 |
| 交易日历 | 以交易所日历和交易session驱动 | 午间休市、开收盘集合竞价、节假日、价格限制/停复牌状态 | 美东时区和夏令时、开收盘竞价、提前收市、延长时段和多场所日历 |
| 订单约束 | 风控检查与市场适配层分离 | 涨跌幅、申报单位、可卖数量、回转交易品种差异、板块状态 | 场所/路由、NBBO口径、价格保护、LULD/暂停、券商限额 |
| 做空/资金 | 订单前查账户和券源状态 | 融券名单、券源和可用量、费率及召回按账户记录 | locate/borrow库存、借券费、Reg SHO义务、券商保证金 |
| 数据源 | 原始行情、时间戳、质量与授权分开记录 | 供应商/交易所授权、竞价/停复牌和证券状态字段 | SIP vs direct feed、报价条件码、venue、延长时段和公司行动 |
| 运营 | 断线恢复、撤单确认、成交对账 | 券商柜台/专线/交易单元状态、系统接入预案 | broker API/FIX session、路由状态、drop copy、借券与清算状态 |

规则须由合规/券商适配层确认，不以策略代码里的手工常量代替。上交所程序化交易实施细则与中国证监会规定有正式生效日期；美国SEC Market Access Rule适用于其规定的经纪交易商市场接入控制场景。具体主体义务依账户和接入方式确认。
