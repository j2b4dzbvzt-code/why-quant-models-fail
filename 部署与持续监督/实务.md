## 1. 生产不是“把回测脚本定时跑起来”

策略上线后，关键事实从“研究时的目标仓位”变成系统在每个时点知道什么、下了什么单、市场实际回了什么。一个可运营的系统必须能回答：

- 当次决策使用的是哪批原始数据、哪个特征版本和哪版模型？
- 数据何时可用、信号何时形成、订单何时提交、成交何时发生？
- 风控检查了哪些限额，哪项通过或拒绝，谁有权调整？
- 本地订单状态和券商状态是否一致？账户里的现金、仓位和应收应付是什么？
- 当输入迟到、模型输出异常、订单重复或风险超限时，系统做了什么？
- 上次已批准版本是什么，怎样恢复且不重复下单？

若无法从审计记录回答这些问题，策略收益无法解释，事故也无法安全处理。

### 1.1 从研究结论到生产契约

生产规格至少包括策略ID、投资主张、市场/证券池、模型和特征版本、数据截止时点、信号频率、交易时段、订单类型、最大规模、费用/借券、风险限额、运行SLO、停止条件和责任人。

将研究假设分级：历史验证、执行代理估计、供应商数据假设、待上线校准。对未验证事项限定额度并指定复核日期。禁止研究笔记中默认的“可成交”“没有延迟”悄悄变成生产事实。

## 2. 生产系统底层架构

建议以分层职责建立系统，不一定每层都是独立微服务：

~~~text
行情/基本面/账户数据源
  → 接入、校验、时间戳和原始事件归档
  → 标准化状态 / 点时特征
  → 模型与策略决策
  → 独立订单前风控
  → OMS / 券商 / 场所适配
  → 成交回报与账户账本
  → 监控、告警、审计和事后分析
~~~

### 2.1 分层的作用

- **数据接入层**负责来源、认证、时间戳、序号、重连、去重和补数。
- **事件/状态层**把乱序、重复消息转成确定性状态；原始事件不可变，修订生成新版本。
- **特征与模型层**只读指定快照和批准工件，不接触券商凭据。
- **组合/风控层**独立检查现金、持仓、敞口、限额和交易可行性。
- **OMS适配层**管理订单ID、提交/确认、部分成交、撤改单和拒单。
- **账本层**将成交、费用、公司行动、现金流和持仓形成对账状态。
- **监控/治理层**负责SLO、告警、变更、批准和复盘证据。

小型低频系统可部署在同一进程或单体服务，前提是模块边界、权限和日志仍然清楚。只有可靠性、团队所有权、延迟或扩容需求支持时才拆服务；服务越多，网络失败、版本错配和数据一致性成本越高。

### 2.2 批处理、流式和低延迟不能用同一SLO

| 模式 | 典型用途 | 主要SLO |
|---|---|---|
| 批处理 | 日频重平衡、财报横截面、组合优化 | 交易日前完成时间、重试可复现、输入完整性、批次对账 |
| 流式事件 | 分钟/逐笔信号、盘中风险更新 | 事件到特征延迟、队列滞后、乱序率、丢包/重连恢复 |
| 低延迟执行 | 高频报价、微观结构策略 | p50/p99和尾延迟、时钟偏差、内存分配、网卡/场所链路 |
| 离线研究/HPC | 参数搜索、特征计算、情景模拟 | 吞吐、资源/成本、确定性、作业失败恢复、输出完整性 |

SLO从策略的“最迟仍有效时点”和风险后果推导。日频因子若可在开盘前几分钟完成，不需要为了极低延迟承担专用系统复杂度；若信号只在某个成交窗口内有意义，则需要明确的端到端延迟预算。

## 3. 数据、特征和模型版本治理

### 3.1 数据契约

每个数据集定义主键、字段、单位、币种、交易所时区、事件时间、可用时间、修订方式、缺失语义、更新频率、最大可接受延迟、授权和负责人。schema改变视作版本变更，不让生产代码通过“缺字段就填0”静默继续。

关键数据质量规则：

- 证券ID和行情/订单时间唯一性、交易日历和session匹配；
- 价格、数量、币种和乘数单位符合市场/产品边界；
- 消息序号单调性、重复/撤回/更正处理一致；
- 关键字段没有未解释的空值、未来时间戳或超新鲜度的数据；
- 输入证券覆盖、分布和活跃状态在预设范围；
- 数据授权、保留期限和传输方式符合供应商合同。

数据缺失要分类：确实没有成交、证券停牌、产品未上市、供应商中断和解析失败不是同一种0。运行时要保存“缺失原因”和采取的降级措施。

### 3.2 离线/在线特征一致性

训练和线上应共享相同的变换定义、字段排序、填补和截尾规则；对每次决策存必要的特征快照或可重建引用。严格记录数据截点，防止线上使用未来可见数据或训练时用了回填版本。

一致性检查可比较抽样样本的离线/线上特征差异：

\[
\Delta_j = |x^{online}_j-x^{offline}_j|
\]

对每个特征设定单位与容忍范围，并记录偏差分布；简单逐点数值相等并不总适用于浮点、滚动状态或延迟数据，差异必须按特征业务定义解释。

### 3.3 不可变发布工件

模型工件绑定源码哈希、权重、依赖、容器/运行时、训练窗、数据版本、随机种子、特征schema、风险配置和市场规则快照。线上不允许自动加载“latest”。新工件先离线重放、生产同构测试、审批，再逐级发布。

即使策略信号和权重不变，只要输入字段解释、券商适配、参数、风险阈值或市场日历改变，都要在变更单中列出差异和验证范围。

## 4. 订单前风险与订单生命周期

### 4.1 独立风控闸门的最小逻辑

订单前风险至少校验：数据是否新鲜、模型版本是否批准、价格/数量是否合法、资金/持仓/卖出可用是否足够、证券/账户是否有交易权限、订单规模是否超限、组合敞口是否超预算、是否重复下单，以及交易时段/停牌/价格限制状态。

下面的教学代码展示hard gate思想，不代替交易所规则解析、券商接口或完整组合计算：

~~~python
from dataclasses import dataclass
from math import isfinite

@dataclass(frozen=True)
class Order:
    client_id: str
    symbol: str
    side: str
    qty: int
    limit_price: float

def pretrade_check(order, snapshot, limits):
    try:
        age = float(snapshot["age_seconds"])
        max_age = float(limits["max_data_age_seconds"])
        max_notional = float(limits["max_order_notional"])
        max_qty = limits["max_order_qty"]
        limit_price = float(order.limit_price)
    except (KeyError, TypeError, ValueError):
        return False, "invalid_risk_inputs"
    if (not isfinite(age) or not isfinite(max_age) or age < 0 or max_age < 0
            or not isfinite(max_notional) or max_notional <= 0
            or not isinstance(max_qty, int) or isinstance(max_qty, bool) or max_qty <= 0):
        return False, "invalid_risk_limits_or_data_age"
    if age > max_age:
        return False, "stale_market_data"
    if (not isinstance(order.client_id, str) or not order.client_id
            or not isinstance(order.symbol, str) or not order.symbol
            or order.side not in {"BUY", "SELL"}
            or not isinstance(order.qty, int) or isinstance(order.qty, bool)
            or not isfinite(limit_price)):
        return False, "invalid_order_fields"
    if order.client_id in snapshot["known_client_ids"]:
        return False, "duplicate_client_order_id"
    if order.qty <= 0 or limit_price <= 0:
        return False, "invalid_order_fields"
    if order.qty > max_qty:
        return False, "order_quantity_limit"
    if order.qty * limit_price > max_notional:
        return False, "order_notional_limit"
    if order.symbol not in snapshot["tradable_symbols"]:
        return False, "symbol_not_tradable"
    if order.side == "SELL":
        sellable = snapshot["sellable_qty"].get(order.symbol, 0)
        try:
            sellable = float(sellable)
        except (TypeError, ValueError):
            return False, "invalid_sellable_quantity"
        if not isfinite(sellable) or sellable < 0:
            return False, "invalid_sellable_quantity"
        if order.qty > sellable:
            return False, "insufficient_sellable_position"
    return True, "approved"
~~~

部署时还需加入买入现金/保证金、价格保护、组合敞口、券源、市场状态、订单频率、自成交防范、盘中损失预算和风控审计。市场单要以保守保护价格/风险口径评估金额，不可把未限定价格订单视作已知notional。额度配置由风控所有，不能和alpha代码一起静默改动。

### 4.2 OMS必须是状态机，而不是发送函数

每个订单有唯一client ID、券商/场所ID和父子关系。管理状态包括创建、风控批准、发送、确认、部分成交、成交、改单、撤单请求、撤单确认、拒单、到期和未知状态。

断线后不要盲目重发：先通过原client ID查询券商状态，再决定是否重试。成交回报可能重复、撤销或修订，按执行ID去重并保留原事件。撤单请求不等于撤单完成，持仓计算基于真实成交，而非本地意图。

### 4.3 Kill switch的动作要与市场状态匹配

至少有策略级、证券级、账户级和全系统级停止开关。可选动作包括：拒绝新开仓、仅允许减仓、取消未完成委托、限制某个场所、停止某一证券或停止全部策略。预先写明控制者、触发条件、券商确认路径和审计日志。

**Kill switch不自动等于市价清仓。** 在停牌、流动性枯竭或市场冲击环境，强行平仓可能加重损失；对已有风险敞口的处置按投资授权和应急预案执行。

## 5. 可靠性：让延迟、失败和重启成为正常设计输入

### 5.1 运行时指标与SLO

实时按策略时钟监控：

- 数据到达和处理延迟的p50/p95/p99、队列滞后、丢失/重复/乱序率；
- 特征/预测完成率、超时、非有限值、异常预测频率；
- 风控拒绝率、订单确认/撤单时长、成交/拒单/部分成交率；
- 持仓和现金对账差异、未解释PnL、账户敞口和额度余量；
- 服务错误率、崩溃重启、CPU/内存/磁盘/网络和密钥到期。

每个SLO按策略容忍时点和损失承受力确定。比如“订单需在开盘前完成”与“每秒更新一个微观结构特征”需要不同的延迟阈值；没有统一的p99毫秒数。

### 5.2 幂等、检查点和恢复

事件处理要幂等：同一行情/成交消息重放不会重复改变状态。记录checkpoint、最后处理序号和版本；重新启动时先恢复持仓、现金、未完成订单和消息位置，再开启新决策。更正数据通过补偿事件或新版本处理，不覆盖已有审计历史。

跨服务必须定义超时、重试次数、退避、断路器和降级行为。风险闸门、持仓状态和订单状态不可因依赖服务超时而跳过。重试交易请求时使用幂等ID，并先查询原状态。

### 5.3 观测日志与敏感信息

日志记录策略ID、模型/配置版本、数据批次、决策ID、风控结果、订单/成交ID和错误码。不要把券商密钥、完整账户凭证或不必要个人数据写入日志。访问控制按最小权限；改参数、解锁kill switch、接入新账户均记录操作者、审批和时间。

## 6. 持续监督：五层监控与分级响应

### 6.1 监控面板

| 层面 | 关键观测 | 常见解释 |
|---|---|---|
| 数据 | 新鲜度、缺失率、覆盖、单位、schema、乱序/重复 | 供应商变化、网络延迟、交易日历错误、证券映射变更 |
| 模型 | 特征和输出分布、校准、置信度、漂移 | 输入环境变了；不一定意味着策略已失效 |
| 策略 | 信号频率、仓位、周转、PnL、回撤、暴露、容量 | 策略机制、风险或配置变化 |
| 执行 | 订单确认、拒绝、成交率、滑点、冲击、借券 | 信号是否可变现、接口/流动性是否变化 |
| 平台 | 延迟、错误、资源、队列、服务状态、重启 | 是否能及时、持续、正确运行 |

收益要按策略持有期成熟后再判断。对于月度标签，每日把未成熟标签记作0会制造虚假退化；只有能用成交、库存或短期代理验证的项目才适合实时报警。

### 6.2 PSI/分布距离是告警线索，不是自动停机按钮

分布漂移可用分箱稳定性指标PSI做初筛：

\[
PSI=\sum_{b=1}^{B}(p_b-q_b)\ln\left(\frac{p_b}{q_b}\right)
\]

其中 \(p_b\) 是参考期分箱占比，\(q_b\) 是当前期占比。分箱、极小占比截断、基准期和观察窗口会影响结果；高PSI不必然说明预测失效，低PSI也不证明条件关系没变。应结合缺失率、模型分数、真实延迟标签、交易成本和暴露一起判断，阈值通过历史压力和误报/漏报成本确定。

重训策略前先排查字段变化、回填、股票池、市场制度、流动性和标签成熟。只因漂移数字升高便自动重训，可能把短期噪声学成新模型；只因短期收益变差便立刻停策略，也可能破坏预设投资周期。

### 6.3 告警分级与处置顺序

| 等级 | 触发示例 | 默认动作 |
|---|---|---|
| 观察 | 单一分布指标变化、低影响延迟 | 记录、查数据和市场状态，不自动改参数 |
| 限制 | 成本/滑点持续恶化、可用券源下降、模型校准退化 | 禁止扩仓、降风险预算、加密人工复核 |
| 停止新单 | 关键输入过期、风险/持仓对账失败、工件版本不匹配 | fail-closed，拒绝新开仓，按预案处理未完成订单 |
| 紧急 | 重复下单、失控敞口、账户/平台重大安全故障 | 启动账户/策略级kill switch、通知责任人和券商、保全日志 |

恢复前核实真实券商订单/持仓、资金状态、时钟和数据版本，确认故障根因及修复，重放未处理事件，取得恢复审批后再逐级放开风险。

## 7. 高频计算和工程优化：书中方法在生产里怎样用

### 7.1 先证明计算结果正确，再做加速

性能优化顺序建议：

1. 运行profile，确认瓶颈是Python循环、重复I/O、序列化、网络、锁竞争还是算法复杂度。
2. 先减少不必要数据和重复计算，使用正确索引/批次/向量化。
3. 按独立任务分块并行；对异质耗时任务做动态队列或过量切分，避免慢任务拖住所有worker。
4. 控制中间结果体积，可在worker输出时归约，不把全部大型对象传回主进程。
5. 只有单机不够且数据/网络成本明确时，考虑分布式/HPC/云。
6. 对优化前后结果做逐列误差、顺序和随机种子核对，并记录资源与运行时间。

第20章“atoms/molecules”思想可翻译为：先划分最小正确计算单元，再组合成任务块；针对不等工作量的任务均衡队列；确定性地归并输出。现代Python用multiprocessing或concurrent.futures时还需考虑进程启动方式、pickle、数据拷贝、线程过度订阅、worker崩溃和可复现排序，不能照搬书中旧版Python代码。

~~~python
from concurrent.futures import ProcessPoolExecutor

def run_chunks(chunks, worker, max_workers):
    # chunks应已按可复算规则编号；map按输入顺序返回，便于稳定归并。
    with ProcessPoolExecutor(max_workers=max_workers) as pool:
        partials = list(pool.map(worker, chunks))
    return partials
~~~

这个骨架没有处理取消、超时、检查点或结果校验；生产任务应给每个chunk一个task ID、输入哈希、重试策略和独立输出位置。多个并行层叠加可能造成CPU过订阅、内存复制和IO争用，需限制总并发数。

### 7.2 向量化、进程池和HPC的收益边界

- **向量化**：用NumPy/编译数组操作代替Python逐元素循环，常改善吞吐；大矩阵也可能因内存峰值变慢。
- **多进程**：适合相互独立、计算密集的任务；启动、pickle、拷贝和IPC成本可能超过任务本身。
- **多线程**：适合I/O密集或释放GIL的库；线程安全、BLAS内部线程数需要协调。
- **分布式/HPC**：适合大规模搜索、矩阵或流数据；数据移动、调度、存储和故障恢复的总成本可能超过算力收益。
- **流式/在线计算**：关注端到端延迟、水位线和状态管理；高吞吐平台未必提供低尾延迟。

每次优化报告墙钟时间、CPU/GPU占用、峰值内存、读写量、输出一致性、复跑波动、失败恢复成本。书中比较的是特定时期的机器和云平台，价格/硬件结论不能直接沿用。

### 7.3 暴力搜索：统计预算和运行预算一起治理

有限离散搜索可用于动态仓位/轨迹、止损、约束组合和小规模参数空间。复杂度通常随资产数、离散水平、持有期和组合约束组合爆炸。上线前要：
- 先估搜索空间大小和上界，设最大CPU/内存/时间预算；
- 确定精确枚举、剪枝、启发式或近似方法及其误差；
- 记录完整候选、停止规则和被看过的输出；
- 评估交易成本、参数不确定性和未来重优化；
- 使用独立锁定样本，防止搜索器自动反复挑测试结果。

书中第21章将动态组合轨迹与交易成本写成离散优化，并讨论量子计算思路。生产系统应将“量子计算能搜索候选”视为方法探索，而不是性能承诺；任何候选都必须验证解质量、硬件可用性、成本和风险限制。经典求解器或分解/近似方案往往更容易复算与审计。

### 7.4 HPC存储、流处理和内存格式

第22章讨论HDF5、并行文件系统、in-situ/in-transit处理、流式分析以及算力与存储架构。迁移到今天的系统时要用实际金融工作负载基准选格式和平台：列式/行式布局、压缩、分区索引、随机读取、追加、并发写、时序查询和GPU搬运的成本都不同。

压缩存储不自动等于更快；大文件顺序读与短窗口随机读特征不同。流式归约可以减少磁盘/网络搬运，但须保存可复算输入和校验值。重要生产数据留不可变原始层，计算缓存可重建；不要把特征缓存误当审计原始记录。

## 8. A股与美股部署细节

### 8.1 A股程序化交易与接口治理

证监会《证券市场程序化交易管理规定（试行）》自2024-10-08施行；上交所程序化交易实施细则自2025-07-07施行。上交所细则涵盖报告、交易行为、信息系统、高频交易和监督检查。生产部署应由合规与券商确认报告、系统接入、账户、系统测试和故障应急要求，不能只检查策略代码能下单。[证监会规定发布公告](https://www.csrc.gov.cn/csrc/c101954/c7480579/content.shtml)；[上交所实施细则](https://www.sse.com.cn/lawandrules/sselawsrules2025/trade/universal/c/c_20250612_10781696.shtml)

对沪深市场分开配置证券状态、停复牌、价格限制、集合竞价时段、申报单位、可卖数量、账户资金和回转类别。A股股票、ETF和其他证券并非同一交易约束。交易日历和接口维护窗口要由实际交易所/券商版本提供，不根据自然日或旧常量推断。

### 8.2 美股经纪商接入、风控和市场数据

SEC Rule 15c3-5针对其定义的经纪商市场接入场景，要求相关经纪交易商建立、记录和维护合理设计的财务/监管风险控制，包括预设资本/信用限额、异常订单拦截、权限控制和执行报告监督；应用时先确认主体与接入方式。[SEC Market Access Rule说明](https://www.sec.gov/rules-regulations/2011/06/risk-management-controls-brokers-or-dealers-market-access)

FINRA算法交易监督材料强调策略上线前测试、系统验证和上线后持续检查。机构应把策略开发、风险、合规和运营放入同一变更链。[FINRA Algorithmic Trading指引](https://www.finra.org/rules-guidance/key-topics/algorithmic-trading)

实务上需区分SIP/综合行情和单场所direct feed，交易时段含美东夏令时、提前收市、开收盘拍卖和盘前盘后；借券和保证金状态需按券商/账户。券商API或FIX session断线后先恢复订单和成交状态，不能直接重放全部发送请求。

### 8.3 跨市场系统

A股和美股收盘不同步；全局组合计算应按信息真实可用时点而非统一自然日切片。服务保存交易所本地时区和UTC，人民币/美元现金与FX定价时点分开；回测、线上特征和监控对齐同一市场日历。美股夏令时切换、A股节假日和跨境通道暂停要成为系统日历事件。

## 9. 书中方法的年代边界与可复用部分

- 第2章金融数据结构、事件驱动bars、ETF trick和CUSUM依然可作为数据加工方法；可交易性、公司行为和点时版本还需连接生产账本。
- 第20章向量化、异步任务、负载均衡、分块和流式归约是可复用的工程原则；代码接口和Python版本须更新。
- 第21章离散优化/全局动态组合展示了问题可形式化的方式；书中量子技术论述属于特定技术时点，不能当作当前可部署性能保证。
- 第22章HPC、HDF5、MPI和在途分析案例说明数据移动、I/O与吞吐可能比算法本身更重要；书中的云/HPC性能价格比较和硬件实例已过时，必须用当下任务重新基准测试。
- 第1、10、11、15、16、19章分别支撑金融ML流程、下注规模、回测偏差、策略风险、配置和市场微观结构；它们提供策略/执行边界，不替代生产风控、模型治理和运维流程。
